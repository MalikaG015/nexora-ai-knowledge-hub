
# Self-Debug Checklists

## Overview

This document provides step-by-step troubleshooting checklists for common integration problems in our fictional payment and shipping platform.

Use these checklists to gather evidence before escalating an incident. Follow the steps in order where practical, record what you observe, and avoid assuming a root cause before verifying it.

## Webhook Not Fired

### Symptoms

A system event occurs, but the configured webhook endpoint does not receive the expected notification. The event may appear successful in the source application even though the receiving system has not processed it.

### Troubleshooting Checklist

1. Confirm that the expected event actually occurred in the source application.
2. Verify that the webhook subscription is enabled for that event type.
3. Check that the configured webhook URL is correct.
4. Verify that the receiving endpoint is reachable from the webhook sender.
5. Inspect webhook delivery logs for the event timestamp and delivery status.
6. Check whether the receiving endpoint returned an HTTP error or timed out.
7. Verify the signing secret and signature validation if the request reached the endpoint but was rejected.
8. Check whether the delivery was retried and whether the retry attempts failed.
9. Confirm that the receiving application is logging incoming requests.
10. Record the event ID, delivery attempt, timestamp, and observed response before escalating.

### Interpreting the Findings

- If no delivery attempt exists, investigate event generation, subscription configuration, and delivery scheduling.
- If delivery attempts exist but fail, inspect the recorded HTTP status, timeout, and error details.
- If the endpoint receives the request but rejects it, investigate request validation, signature verification, and application logs.
- If delivery succeeds but the expected action does not occur, investigate processing logic in the receiving application.

These findings guide the investigation but do not prove a single root cause.

## Blank Shipping Label PDF

### Symptoms

A shipping label PDF is generated or downloaded, but the document appears blank, incomplete, or missing expected label details.

### Troubleshooting Checklist

1. Confirm that the shipping-label generation request completed successfully.
2. Check the API response status and response body.
3. Verify that the response contains a non-empty PDF or a valid reference to the generated file.
4. Confirm that the downloaded file is the response for the correct shipment.
5. Check whether the shipment contains the required recipient, address, and package information.
6. Verify that the selected carrier and service support label generation for the shipment.
7. Inspect application logs for PDF-generation errors or external carrier errors.
8. If the PDF is generated by an external provider, check the provider response and any returned document URL.
9. Open the file in another PDF viewer to rule out a viewer-specific rendering issue.
10. Record the shipment ID, request timestamp, response status, and relevant error details.

### Interpreting the Findings

- An empty response may indicate that the document was not returned as expected.
- Missing shipment information may prevent the label from being generated correctly.
- A successful API response does not necessarily prove that the PDF contains valid, visible label content.
- If the file contains visible content in another viewer, investigate the original viewer or rendering environment.

Do not assume the carrier is responsible until the request, response, and generated document have been inspected.

## Tracking Number Missing

### Symptoms

A shipment has been created, but the application does not display a tracking number or the tracking number is missing from the API response.

### Troubleshooting Checklist

1. Confirm that the shipment-creation request completed successfully.
2. Retrieve the current shipment status using the shipment ID.
3. Check whether the carrier has assigned a tracking number yet.
4. Inspect the shipment API response for the tracking-number field.
5. Review application logs for carrier API errors or response-parsing failures.
6. Check whether the shipment is still pending or awaiting carrier confirmation.
7. Verify that the application maps the carrier's tracking-number field correctly.
8. Check whether an asynchronous update or webhook is required to populate tracking information.
9. Inspect webhook delivery logs if the application depends on a shipment-update event.
10. Record the shipment ID, carrier, creation timestamp, API response, and relevant logs.

### Interpreting the Findings

- If the carrier has not assigned a tracking number, investigate shipment processing status.
- If the carrier response contains a tracking number but the application does not display it, investigate data mapping and persistence.
- If the application depends on a webhook, verify that the event was delivered and processed.
- If the response is incomplete or the carrier request failed, investigate the corresponding error details.

Do not invent a tracking number or treat a shipment as dispatched without supporting evidence.

## Escalation Checklist

Before escalating any of these problems, collect:

- The affected shipment, event, or request ID.
- The approximate start time and timezone.
- The affected endpoint or operation.
- The observed HTTP status and error message.
- Relevant application and delivery logs.
- Recent deployments or configuration changes.
- Diagnostic steps already performed and their results.

Clearly distinguish confirmed observations from hypotheses. If the available evidence is insufficient, state what is unknown and identify the next diagnostic step.
